# 洞察引擎演进分析

## 1. 概述
`InsightEngine` 经历了一次重大的架构转变，从 **基于模板的系统** 转变为 **逻辑驱动的推理引擎**。本文分析了这一转变背后的原因及其对 Morning Goal 应用“个性化 AI”（第5阶段）目标的益处。

## 2. 传统方法：模板系统
**文件：** `InsightTemplate.swift`

之前的版本依赖于一个静态的 `InsightTemplate` 对象库。
- **机制：** 字符串替换（例如，将 `{{count}}` 替换为数字）。
- **触发：** 基于单一事件计数器的简单触发。
- **局限性：** 它本质上是数据的“填词游戏”——仅仅是填空。它缺乏对*上下文*的理解。
  - *例子：* 它可以说“你有5个目标”，但无法验证这些目标是否本质上是冲突的（例如，高紧急度 vs 低能量）。

## 3. 新方法：逻辑引擎
**文件：** `InsightEngine.swift`

当前版本实现了一个基于规则的推理引擎，充当“洞察协调者”。
- **机制：** 条件逻辑与数据聚合（`GoalDataAggregator`）。
- **情境感知：** 它直接访问 Core Data 上下文，允许其实时查询历史趋势、分布，并交叉引用数据点。
- **优先级瀑布流：** 它实现了一个决策树（里程碑 -> 紧急度 -> 平衡 -> 模式 -> 趋势），以确用户看到的不仅仅是第一个被触发的洞察，而是*最相关*的洞察。

## 4. 关键差异与变革驱动力

### A. 从“是什么”到“为什么”
- **旧：** “你做了 X。”（描述性）
- **新：** “你非常关注 X，也许试试 Y？”（规范性/建议性）
- **原因：** 为了提供真正的*价值*，AI 需要解释数据，而不仅仅是展示数据。转向逻辑块允许进行“复杂事件处理”（CEP）。

### B. 多维度支持
- **旧：** 只知道 `Category`（类别）和基本计数器。
- **新：** 专为利用5个新维度（`Urgency` 紧急度, `TimeFrame` 时间范围, `ActionType` 行动类型, `Difficulty` 难度, `Specificity` 具体程度）而构建。
- **原因：** `InsightTemplate` 太过僵化，无法处理7个维度的组合爆炸。对于复杂条件，代码逻辑（`if/else`）比字符串模板更具扩展性。

### C. 动态聚合
- **旧：** 依赖于传入的预计算值。
- **新：** `InsightEngine` 拥有一个 `aggregator`（聚合器）。它可以即时提出复杂问题：*“周一‘工作’目标的紧急度分布是怎样的？”*
- **原因：** 深度个性化需要按需查询，而不仅仅是预计算的统计数据。

## 5. 原未来可扩展性
这次重构为以下方面奠定了基础：
- **机器学习集成：** `InsightEngine` 可以轻松扩展以调用 CoreML `InsightModelManager` 来验证其基于规则的直觉。
- **用户反馈循环：** 引擎中的 `priority`（优先级）系统可以根据用户“喜欢”或“采取行动”的洞察进行动态调整（轻量级强化学习）。

## 结论
从 `InsightTemplate` 到 `InsightEngine` 的过渡代表了从 **报告** 到 **推理** 的转变。虽然 `InsightTemplate` 对于*格式化*输出（视图层）仍然有用，但 `InsightEngine` 现在理所当然地拥有生成洞察本身的*业务逻辑*。
