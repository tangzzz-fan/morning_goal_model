# 端侧 AI 技术规划与功能点评估（基于 data_insights_readme.md）

## 1. 技术规划与架构评估（端侧 AI）

### 1.1 端侧系统分层

**目标拆解：将“记录文本”稳定转化为“可计算的结构化事件 + 向量表征 + 洞察结论”。**

**A. 语义解析层（F1）**
- 输入：用户文本、时间戳、可选上下文（地点、日程、是否完成等）
- 输出：多标签主题、情绪分值、精力等级、实体（时长/事项）、文本向量（Embedding）
- 运行模式：前台触发 + 后台异步补全（避免阻塞 UI）

**B. 洞察引擎（F2）**
- 输入：过去 N 天结构化数据与向量
- 输出：聚类主题簇、时间段规律、趋势/预警、关联规则
- 运行模式：启动/充电/闲置批处理（控制电量），增量更新（避免全量重算）

**C. 可视化层（Dashboard）**
- 输入：洞察结论（可解释、可追溯到原记录）
- 输出：周/月报卡片、即时提示、可点击回溯“高光时刻”

### 1.2 模型与算法选型（按功能点）

**F1.1 意图与类别自动识别（多标签）**
- 现状对齐：当前仓库已实现“主题 + 情感”的多任务分类结构，可作为 F1.1/F1.2 的统一骨架（共享编码器 + 多头）。
- 规划：从单标签 16 类升级为多标签 16 类（Sigmoid + BCEWithLogitsLoss），支持一条记录多类命中。
- 推理输出：Top-K 标签 + 置信度，配合阈值（per-label threshold）与温度校准（避免过度自信）。
- 验收口径落地：将“准确率 > 85%”改写为可执行指标：micro-F1、macro-F1、Precision@K、标签修正率（线上）。

**F1.2 隐性情绪计算（Score + Energy）**
- 规划一：情绪三分类 + 分值映射
  - 分类头输出 P(neg), P(neu), P(pos)
  - Sentiment Score = P(pos) - P(neg)，范围 [-1, 1]
- 规划二：增加回归头
  - 直接回归 sentiment_score（HuberLoss），并保留三分类用于可解释展示
  - Energy Level 回归到 [0, 10]，可使用 sigmoid 缩放：energy = 10 * sigmoid(logit)
- 端侧稳态：分值输出必须做置信区间/平滑（EWMA），避免单条文本导致曲线大幅抖动。

**F1.3 实体抽取（时长、事项实体）**
- 时长：端侧优先规则引擎（正则 + 数字中文归一 + 单位换算），覆盖“2小时/半小时/30min/一刻钟”。
- 事项实体：P1 范围内采用轻量 NER（token classification），或使用“聚类关键词 + 规则短语表”替代（降低模型体积）。

**F2.1 生活重心热力聚类（Embedding + 聚类）**
- 向量来源：与 F1 共用编码器，输出 pooled embedding；存储 float16（或量化）以控体积。
- 聚类：MiniBatchKMeans（增量友好）或 HDBSCAN（无需 K，但端侧实现/性能更难控）。
- K 的选择：基于过去 30 天，限定 K 范围（例如 6–20），用轮廓系数/CH 指数选择并设置稳定性约束（避免频繁跳变）。

**F2.2 黄金时间段识别（环形统计 + 关联）**
- 将一天映射为角度 θ，按 Sentiment Score/完成率做加权平均向量，得到峰值时间段。
- 输出需包含置信度与样本量门槛（例如近 14 天有效样本 ≥ 10）。

**F2.3 倦怠预警（趋势与异常）**
- 指标：Text Length、负向情绪分值、记录频率、主题分布熵。
- 算法：EWMA + 变化点检测（CUSUM）或简单规则组合。
- 预警策略：触发后进入冷却期（例如 72 小时不重复弹窗），并提供可解释证据（连续 N 天趋势）。

**F2.4 隐性习惯关联（规则挖掘）**
- 事务定义：以“天/半天/会话”为 transaction，将标签、聚类簇、时段离散桶、完成情况编码成 item。
- 规则：Apriori/FP-Growth，输出 support/confidence/lift，并对多重检验做约束（最低支持度 + 稳定性）。
- 输出必须可解释并可回溯原始样本，禁止生成不可验证的因果措辞。

### 1.3 端侧工程化落地（iOS）

**模型格式与体积（40MB 约束）**
- 导出：训练侧 PyTorch → CoreML `.mlpackage`。
- 压缩路径：优先 float16 权重量化；如需进一步缩小，采用 int8 量化（需校准集）。
- 切分策略：将“主干编码器”与“任务头”整体导出为单模型，避免多次编码开销。

**推理时延（200ms 约束）**
- Tokenization 与推理解耦：Tokenizer 运行在 CPU，推理走 ANE/GPU；采用异步队列并限流。
- 缓存：对重复/相近文本做 embedding 缓存（hash + LRU），减少重复推理。
- 批处理：洞察引擎批跑时使用小 batch（例如 8–16）降低总耗时与能耗。

**数据存储与擦除（Privacy First）**
- 原文、结构化字段、向量、洞察缓存必须分层存储，并支持级联物理删除。
- 向量存储：建议单独文件/表（按 entry_id 索引），删除时同步删向量与派生缓存。
- 加密：数据库与向量文件启用 at-rest 加密（iOS Keychain 派生密钥）。

### 1.4 评测体系与验收闭环

**离线评测（模型训练/回归测试）**
- F1.1（多标签）：micro-F1、macro-F1、Precision@K、Recall@K、标签覆盖率。
- F1.2（分值）：三分类 accuracy/F1 + 分值相关性（Spearman）+ 校准误差（ECE）。
- F1.3（NER）：实体级 Precision/Recall/F1，按“时长”与“事项”分别统计。
- 端侧性能：模型体积、冷启动耗时、p95 推理时延、峰值内存、批处理能耗。

**线上指标（隐私约束下的产品度量）**
- 标签修正率（越低越好）、洞察卡片 CTR、预警关闭率、周报展开率、功能留存提升。

### 1.5 与现有代码仓库的对齐（实现落点）

- 多任务骨架：以现有“主题 + 情绪”多头模型为主线，扩展为多标签与回归头。
- CoreML 导出：已具备导出入口与 Colab 流程，可作为 iOS 端集成的产物来源。

## 2. 功能点评估（可交付性、风险、验收）

| 功能点 | 可交付性 | 主要依赖 | 关键风险 | 验收口径落地 |
| --- | --- | --- | --- | --- |
| F1.1 多标签类别识别 | 高 | 标注体系、阈值校准 | 标签粒度不稳定、类间重叠 | micro/macro-F1、P@K、修正率 |
| F1.2 情绪分值与精力 | 中 | 情绪标注/弱标注、平滑策略 | 分值抖动、可解释性不足 | 分类 F1 + 分值相关性 + 曲线稳定性 |
| F1.3 时长与事项实体 | 时长高/事项中 | 规则库、NER 数据 | 口语表达多样、误识别成本 | 时长抽取准确率、实体 F1 |
| F2.1 聚类主题簇 | 中 | embedding 稳定性、增量聚类 | 簇漂移、K 不稳定 | 稳定性约束 + 可回溯样本 |
| F2.2 黄金时间段 | 高 | 时间戳质量、样本量 | 小样本误判 | 置信度 + 样本门槛 |
| F2.3 倦怠预警 | 中 | 趋势特征、冷却策略 | 误报带来干扰 | 误报率、用户关闭率、解释证据 |
| F2.4 关联规则 | 中偏低 | 数据量、离散化策略 | 虚假相关、因果误导 | lift/稳定性门槛 + 样本回溯 |

## 3. 技术分期交付清单（对应 Roadmap）

**Phase 2.1（MVP）**
- 端侧多标签分类（F1.1）+ 时长规则抽取（F1.3-时长）
- 情绪三分类 + 分值映射（F1.2 基线）
- CoreML float16 导出与 iOS 推理链路打通（体积与时延基线）

**Phase 2.2（Intelligence）**
- embedding 存储与增量聚类（F2.1）
- 周报基础聚合与可回溯“高光时刻”（Dashboard A）

**Phase 2.3（Pro）**
- 倦怠预警（F2.3）与关联规则（F2.4）
- 情绪/精力回归头与校准（F1.2 增强），完善即时洞察卡片（Dashboard B）
